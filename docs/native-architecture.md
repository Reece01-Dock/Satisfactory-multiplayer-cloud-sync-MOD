# Native architecture: the mod is the application

Status: **adopted** (supersedes the helper-centric design in `architecture.md`,
which stays valid as the description of the reference implementation).

## 0. Audit of the starting point

| Area | State at audit (commit `b80c168`) |
|---|---|
| `shared-world-helper/` (Go) | Complete reference implementation: CAS record, lease + fencing, verified download, fenced upload, recovery, world state machine, localhost IPC. 45+ tests incl. races 1–6. Windows CI found one real bug (fsync on a read-only handle), fixed in `b80c168`. |
| `shared-world-mod/` (C++) | Thin client: polls the helper over HTTP, launches `shared-world-helper.exe`, drives `LoadSaveFile` / `JoinSession`. Not compiled. |
| `docs/architecture.md`, `docs/ipc-protocol.md` | Describe helper + IPC. IPC is now slated for removal. |
| `STATUS.md` | World creation only via IPC; no cloud provider; mod unverified in game. |

What must be preserved (the behavioural spec): exactly one host under
simultaneous Play; generation fencing of every write; revision N never
replaces N+1; verified, atomic local replacement; structural save
validation (every zlib chunk); unsynced-progress recovery; conflict backups
instead of overwrites; ambiguous-commit resolution.

No helper process, no localhost server, no external `git.exe`.

### Steam / Epic

The mod uses Steam/Epic **through the game**: identity
(`ULocalPlayer::GetPreferredUniqueNetId`), friend presence and session
publication/joining (the game's OnlineIntegration / EOS layer,
`docs/research.md` §4). They are *not* used for shared storage or locking:

* Steam Remote Storage and EOS Player Data Storage are per-user; friends
  cannot read or conditionally update each other's files.
* EOS Title Storage is read-only for clients; Steam Workshop is not
  enabled as a general file store for Satisfactory; neither offers
  compare-and-swap.
* Using Coffee Stain's EOS deployment credentials for our own data would
  be outside what the game's client is authorised for.

So storage/coordination needs a provider the players control (a private
GitHub repository first; S3/R2 later). Everything else stays in-game.

## 4. Git / storage design

### Findings that drove it

* GitHub: Git objects hard-blocked at 100 MiB, recommended ≤ 1 MB;
  repository on-disk size recommended ≤ 10 GB; push ≤ 2 GB.
* Git LFS on Free/Pro: 10 GiB storage + 10 GiB bandwidth per month.
  Four players downloading a 50 MB save daily ≈ 6 GB/month: too tight.
* Release assets: each < 2 GiB, 1000 per release, **no limit on total
  size or bandwidth**; downloadable with the same token.
* **Benchmark** (`shared-world-helper/tools/benchsave`, synthetic saves in
  the real container format, 1 % of objects changed + 500 new per
  revision): 10 revisions = 86.8 MiB raw → 86.7 MiB after
  `git gc --aggressive`; **0 of 238 compressed chunks reused** between
  consecutive revisions. zlib chunking defeats Git deltas: every revision
  costs its full size in Git. (Synthetic; to be re-run on real saves.)

Conclusion: **Git holds metadata and history; save bytes live in a
content-addressed object store.**

### Repository layout (one branch: `shared-world`)

```
world.json                     immutable identity: schema, worldId (uuid), name,
                               createdBy, createdAt, originalSaveName, gameBuild, modVersion
state/current.json             THE authoritative document (CAS domain): stateVersion,
                               generation, head revision, lease, lastSession
state/players.json             members + roles
state/settings.json            sync frequency, migration, retention, preferred hosts
revisions/00000152-g00000027-3f2a1c9e.json
                               immutable revision metadata (sha256, size, object,
                               previous, generation, uploader, reason, game/mod versions)
recovery/                      recovery reports (peer candidates), immutable
```

Object store: `objects/sha256/3f/3f2a…` (filesystem) or release assets
named `3f2a….sav` in releases `shared-world-objects-<n>` (GitHub).

### Commits

Every state change is one commit on `shared-world`, created with the
Git Data API (`POST git/trees` with `base_tree`, `POST git/commits` with
exactly one parent = the tip we read, `PATCH git/refs/heads/shared-world`
with `force: false`). Commit messages are human-readable, e.g.

```
Shared World revision 152

World: My Factory
Player: Reece
Generation: 27
Reason: autosave
Save SHA256: 3f2a…
Previous Revision: 151
```

Heartbeats are commits too (`Heartbeat: generation 27`); History UI reads
`revisions/`, not the commit log, so they do not clutter it. No secrets are
ever written to the repository.

There is one authoritative branch. No player branches, no merges, and no
merge conflict can surface: a lost CAS race means re-read and re-decide.

## 5. Concurrency model

**The CAS primitive** is "move `shared-world` from commit P to commit C,
where C's only parent is P". A fast-forward-only ref update of a
single-parent commit succeeds iff the tip is still P (the ref can only
move backwards by force-push, which the mod never does and branch
protection can forbid). Equivalent primitives: filesystem lock + rename
(Filesystem provider), `If-Match` (S3/R2, later).

On top of it, unchanged from the helper:

* `state/current.json.generation` is the fencing token; acquisition
  increments it. Every mutating operation (renew, commit revision,
  publish session, release, migration handoff) checks
  `generation == mine && lease.nonce == mine` inside the same CAS.
* Committing revision N+1 additionally requires `head == N`.
* Lease expiry for *others* is judged with a skew grace; a host that was
  offline but not replaced may renew (nobody else could have written).
* **Git is not the lock.** Pushing history is not what grants authority;
  the fenced state document inside the CAS'd commit is.
* Objects are uploaded *before* the commit that references them and are
  immutable and content-addressed: an upload can never damage anything,
  and an uploaded object only becomes current through the fenced commit.
* Ambiguous outcomes (response lost) are resolved by re-reading the tip.

GitHub budget: each state commit costs 3 content-creating requests.
With heartbeat 90 s / TTL 300 s a host uses ≈ 120/hour of the 500/hour
secondary limit; revisions every 10 min add 18/hour.

## 6. Save-object model

* Object id = lowercase hex SHA-256 of the exact `.sav` bytes.
* `Put(hash, file)`: skip if present (dedup), upload, read back / stat and
  verify size + hash.
* Revision metadata references the object; `state/current.json.head`
  references the revision. Restore of revision 140 = new revision 153
  pointing at revision 140's object (no history rewrite, no re-upload).
* Local cache `%LOCALAPPDATA%/SatisfactorySharedWorld/cache/objects/…`
  holds verified objects; migration and restore reuse it. The cache never
  decides what is authoritative.
* Retention (later): objects referenced by the last N revisions are kept;
  older ones become deletable; conflict/recovery objects are never auto-deleted.

## 7. Recovery and migration

* **Unsynced local progress** (port): on Play, a local save that differs
  from the last synced hash is uploaded if and only if the head is still
  the revision it was based on; otherwise preserved as a recovery backup.
* **Planned migration**: host saves → validates → uploads → commits
  revision R (fenced) → writes `lease.handoff = {successor, revision R,
  expiresAt}` (fenced) → releases. The successor waits for the release,
  acquires generation+1 via normal CAS (the handoff reservation lets only
  the chosen successor acquire during a short window), downloads exactly R,
  hosts, publishes the session; other clients see the new session and
  reconnect. Authority never exists in two places: the successor's
  acquisition is an ordinary fenced CAS.
* **Successor choice** (deterministic, pure function): eligible clients
  (compatible versions, storage reachable) ranked by has-object-cached,
  then ping, then player id.
* **Crash**: lease expires; clients' recovery reports (`recovery/…`:
  generation, base revision, object hash, validated flag) are considered;
  a candidate is accepted only if its generation equals the crashed
  lease's generation, its base revision equals head, its object is present
  and validates. Deterministic choice among equal candidates (newest save
  time, then hash). Otherwise fall back to head. Never "newest timestamp wins".

## 8. Authentication

* GitHub OAuth **device flow** (only a client id is shipped; no secret):
  the mod shows the code + URL, polls at the server's `interval`.
  Requires registering an OAuth App for the project (owner action).
* Token stored with Windows Credential Manager (`CredWriteW`, target
  `SatisfactorySharedWorld:github`); never in the save, repo, logs or UI.
* Filesystem provider needs no credentials.

## 9. Directory structure

```
shared-world-mod/
  SharedWorld/                        SML plugin
    Source/SharedWorldCore/           pure C++20 core (UE module + CMake)
      Public/SharedWorldCore/{Util,Model,Save,Storage,Lease,Sync,World,Recovery,Migration,Providers}
      Private/…
    Source/SharedWorld/               UE module: Game/, UI/, Auth/, Platform/
  core-tests/                         CMake project: builds core + unit tests natively
```

Core rules (so it compiles unchanged inside Unreal): C++20, no exceptions,
no RTTI, no UE headers, no identifiers that collide with UE macros
(`check`, `verify`, `ensure`), `(std::min)` style to survive `windows.h`.

## 11. Major risks

| Risk | Mitigation |
|---|---|
| Cannot compile/run UE here | Core is UE-free and fully tested natively; UE layer kept thin; explicit runtime checklist |
| GitHub ref CAS semantics under concurrency not verifiable without a live repo | Documented FF-only semantics; fake enforces them; live validation task; S3 `If-Match` provider as alternative |
| GitHub secondary rate limits | 90 s heartbeat, backoff on 403/429 honouring `retry-after`, budget in §5 |
| Release assets as object store is unconventional | Behind `IObjectStore`; S3/R2 provider next |
| Game join/load APIs unverified at runtime | Isolated in `Game/`; blockers tracked in STATUS |
| Large saves on game thread | All hashing/IO/network on worker threads; game thread only marshals results |
| Peer recovery accepting a bad save | Strict acceptance rules (generation, base, hash, validation); deterministic choice; tests |
